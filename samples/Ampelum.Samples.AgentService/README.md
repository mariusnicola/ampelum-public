# Agent as a service

A program is served over HTTP by the Ampelum Host, a client drives every Host endpoint, the tool is also served as an MCP server and called back, a tool agent uses MCP tools, and the REPL and the CLI commands are run against the same answers.

`Program.cs` runs these parts in order:

1. **Host.** `AgentServiceHost.cs` serves one `Predict<AnswerSignature>` module with `AddAmpelumHost`, `MapAmpelumModule` and `MapAmpelumHostEndpoints`. `AgentServiceClient.cs` calls, in `Program.cs` order: `/modules`, `/healthz`, `POST /modules/Answer/forward`, `/audit`, `/audit/verify`, `POST /modules/Answer/stream` (`partial`, `final`, `done` frames), `GET /audit/{traceId}`, `POST /audit/replay/{traceId}`, the prompt endpoints (create a challenger, promote it, read the active version, list), `POST /admin/rebuild-index` (it must keep the prompt versions and the promotion), the optimize endpoints (start, status, SSE stream), and `/openapi/v1.json`. `/readyz` is covered by the tests.
2. **Host CLI.** `CliTools.cs` runs the Host's own `rebuild-index` command as a process against an audit file under `./data` in its working directory.
3. **MCP tools.** `ToolAgent.cs` loads tools through `McpToolFactory.FromMcpSessionAsync` and hands them to a `ReAct` agent. A second path surveys tools through `McpToolSource` and an `IMcpTransport`.
4. **MCP server.** `OrderMcpServer.cs` serves the order tool. `McpServerAdapter` answers `tools/list` and `tools/call` but the library has no transport for it, so this file is the transport: JSON-RPC 2.0 over one POST route on `127.0.0.1`, the wire shape `HttpMcpTransport` speaks. Every call goes through `ToolDispatcher`, so policy and the tool audit log apply. `McpClientSide.cs` turns any `IMcpTransport` into the agent's tools. The sample then calls its own server with the library's `SdkMcpTransport` (the official MCP client, over HTTP) for `tools/list` and `tools/call`, surveys it, and runs the `ReAct` agent through it. The server answers `initialize` and `ping` too, because the SDK client needs them; `HttpMcpTransport`, the older transport, does not.
4a. **Governed MCP over HTTP and stdio.** `OrderMcpStdio.cs` holds `GovernedMcpClient`: `McpToolSource` lists the server's tools, `RegisterHandlersAsync` makes them callable through `ToolDispatcher`, and a call goes policy first, `tools/call` only if allowed. Over HTTP the sample runs it twice against its own server: with no verifier the tool is capped to the most dangerous tier and blocked, and `OrderMcpServer.ReceivedToolCalls` shows the server saw no call; with `DeclaredTierVerifier` the call goes through. Over stdio the sample starts itself again with `--mcp-stdio-server` as a child process (`SdkMcpTransport.CreateStdio`) that serves `lookup_order` (declares Safe), `purge_orders` (declares Catastrophic) and `note_order` (declares nothing). Only `lookup_order` runs; the other two are blocked, and the child's call log, written before each tool runs, lists only `lookup_order`. Disposing the transport ends the child, and the sample checks that through the child's own process object (found from a pid file the child wrote) without stopping anything.
5. **REPL.** `ReplSession.cs` feeds a script to `ReplLoop`, which evaluates it with Roslyn against the model.
6. **CLI.** `CliEval.cs` writes the service's answer to a JSONL file and runs `ampelum eval` on it as a process. `CliTools.cs` runs `ampelum new` for the `ampelum-agent` template into a temp folder and `ampelum repl` with a blank key. Every process has a time limit after which it is stopped. `eval` runs only with `--fake`: the reference answer is the scripted one, so a live model has nothing valid to be scored against.

## Use cases

A program written once is served as an HTTP service by the Ampelum Host: the sample calls it, streams it, reads its hash-chained audit by trace id, replays a recorded call without the model, stores and promotes prompt versions, starts optimizer runs and follows their progress over SSE, and rebuilds the Host's index from the audit file with the admin endpoint and with the Host's own command line. The same order tool is served as an MCP server on loopback and consumed back through the library's SDK transport, both by a direct `tools/call` and by a `ReAct` agent, and the governed MCP path is shown over HTTP and over a stdio child process, where a catastrophic or unannotated tool is blocked before the server receives the call. The Ampelum CLI is shown by scoring answers with `eval`, scaffolding a project with `new`, and refusing to start `repl` without a key. Several Host features are plumbing with known defects, listed below and pinned by tests.

## Run with a scripted model

```
dotnet run --project samples/Ampelum.Samples.AgentService/Ampelum.Samples.AgentService.csproj -c Release -- --fake
```

No key and no network beyond `127.0.0.1` are needed. The scripted answers live in `FakeScript.cs`. The exit code is 0 when the audit chain verifies, the stream ends in `final` then `done` with no `error` frame, health, replay, prompts, optimize, OpenAPI, the Host CLI and the MCP round trips (HTTP, governed HTTP, governed stdio with the child exited) each succeed, the REPL reports no error, `eval` exits 0, `ampelum new` writes six files, and `ampelum repl` refuses and names `OPENROUTER_API_KEY`.

## Run against a live model

Without `--fake` the sample reads `OPENROUTER_API_KEY` and `OPENROUTER_MODEL_1` from `.env` (copy `.sample.env` to `.env` and fill them in) or from environment variables. The same key is passed to the Host as `Host:OpenRouter:ApiKey`, which the Host requires whenever a module is mapped. A live run sends one extra model call per optimizer training example (two). The live path has never been run for this sample; only `--fake` and the tests have. `ampelum repl` is never run live; only its refusal is.

## Tests

```
dotnet test tests/Ampelum.Samples.AgentService.Tests/Ampelum.Samples.AgentService.Tests.csproj -c Release
```

The Host and MCP tests run on an in-memory `TestServer`, with MCP tests on a real loopback socket. `McpSdkTests` starts the sample's own assembly as the stdio child under the `dotnet` host (the running one when it is dotnet, otherwise the first `dotnet` on the path), so no app host file or execute bit is needed and the tests run the same on Linux. The CLI tests start the built CLI and the Host as processes, found from the .NET runtime directory rather than `PATH`. `ampelum new` is tested against a template-engine home private to the run, so the machine's template list is not touched. Tests named `KnownLimit_` assert a defect of the library as it is today; when the library is fixed they fail and the pin is to be removed.

## What the sample works around

- **Audit sink, swapped.** The original sample used the in-memory sink that `AddAuditHook` falls back to. It now uses a file-backed sink, because the Host builds its audit index (audit by trace id, replay) only from `Host:Storage:AuditFile`, and nothing else writes that file.
- **CLI runtime.** Checked: started from the sample's output folder with the CLI's own runtime settings, `ampelum repl` stopped with `FileNotFoundException` for `Microsoft.Extensions.Logging.Abstractions` 10.0.0.0, while the same command started from the CLI project's own output folder, and through `dotnet exec --runtimeconfig` with the sample's runtime settings, reached its key check. The sample runs every CLI command through `dotnet exec --runtimeconfig`. I did not check other commands or other folder layouts, and I did not find out why the CLI's output folder has the assembly while the sample's does not.

## What does not work, and why

- **Optimize is plumbing.** The Host's metric is the private `NoOpMetric` and returns 1.0 for every pair (`PredictComposedAdapter.cs:70`), and `BootstrapFewShot` keeps the module's own answer as the demonstration whatever the label says. A run therefore tunes nothing. The endpoints (start, status, SSE progress, final, done) are shown and tested as plumbing; `KnownLimit_TheHostsOptimizeMetricScoresEveryPairOne` reaches the private class by reflection and `KnownLimit_OptimizeKeepsTheModelsAnswerWhateverTheLabelSays` shows the effect. For a finished run the stream rebuilds `final` from the stored row with empty demonstrations (`OptimizeEndpoint.cs:172` onward, the terminal-state branch of `StreamOptimizeAsync`), so the live frames are the ones to read.
- **Audit lookup reads the file for an unindexed call.** A forward call does not write the audit index. `GET /audit/{traceId}` and `POST /audit/replay/{traceId}` ask one lookup (`AuditEntryLookup`), which uses the index row when there is one and otherwise reads the audit file, so both work before any rebuild (`AuditByTrace_ReturnsTheRecordedCall_WithoutARebuild`, `Replay_ServesTheRecordedAnswer_WithoutARebuild`). The price is one scan of the file per lookup of an unindexed entry, an unknown id scans all of it, and an index row that points at a sequence the file no longer holds answers 404 without a scan.
- **Rebuild keeps the prompt versions and which one is active.** Creating a version and every promotion write the version's module, id, status, parent and note into the file's `_meta` block (the block the optimizer writes), by temp file and move. `rebuild-index` empties the prompt table and refills it from every `.json` file under the prompt folder, reading `_meta` when the file has one (`RebuildIndex_KeepsWhichPromptVersionWasPromoted_AndForwardStillUsesIt`, `..._AndStreamStillUsesIt`, `RebuildIndex_KeepsThePreviousActiveVersionRetired`), so the promoted version is active again and an optimizer file is listed under its own module and version id. A file without a readable `_meta` (written by an earlier Host, or not JSON) falls back to the folder name as the module, the file name as the version id, the last write time as the date, and status challenger; a promotion made before this change was only in the index, so such a file comes back as a challenger. If two files claim active for one module, the newest stays active and the other comes back retired.
- **Promoted prompts apply to the `default` submodule only.** `POST /modules/{name}/forward` and `POST /modules/{name}/stream` load the active prompt version (or the one named in `PromptVersionId`) and send its `default` instruction override and its `default` demonstrations to the model for that call (`Forward_SendsThePromotedVersionsDemonstrations_AndItsInstruction`, `Forward_SendsAVersionsDemonstrations_EvenWhenItHasNoInstruction`, `Stream_SendsThePromotedVersionsDemonstrations`, `Stream_SendsThePromotedInstruction_AndTheFinalFrameNamesTheVersion`, `Forward_SendsThePromotedInstruction_AndReportsTheVersionUsed`, `Forward_UsesTheVersionPromotedLast`, `Forward_WithAnExplicitVersionId_SendsThatVersionEvenWhenItIsNotPromoted`); the response names the version used, and an unknown id answers 404 `VersionNotFound` before any model call. Only the `default` key is read, because the module is one `Predict`; demos a caller passes to the module itself still win over the version's. A file an earlier Host wrote, with `Inputs` and `Outputs` in Pascal case, is read both ways: the list endpoint shows its demonstrations and a call sends them (`Forward_AVersionFileWrittenWithPascalCaseDemonstrations_SendsItsInstructionAndItsDemonstration`); an example with neither inputs nor outputs is left out (`Forward_AnExampleWithNeitherInputsNorOutputs_IsLeftOut_AndTheOthersAreSent`). A version file that cannot be read makes a forward call fail with the Host's "Forward call failed" 400 and a stream call with a plain JSON "Stream failed" 400 before the event stream starts; an unknown or foreign version id answers a plain JSON 404 the same way. The final frame of a stream names the version used. The sample's `--fake` run forwards and streams once after promoting and checks the scripted model was sent the instruction and the demonstration both times. Demonstrations now read back with their inputs and outputs (`PromptDemoExamples_AreStoredWithCamelCaseNames_AndReadBackWithTheirInputsAndOutputs`).
- **Host CLI `rebuild-index --config <path>` ignores the path.** `Program.cs:17` passes the arguments on with `rebuild-index` still first, and `HostCli.cs:20` only reads `--config` when it is `args[0]`, so the path is never used and `appsettings.json` is always the file. Verified by running it with a config naming other storage: it indexed `./data` and never opened the named file (`KnownLimit_HostRebuildIndex_IgnoresThePathGivenToConfig`).
- **Host CLI settings file.** The command reads the `appsettings.json` in its working directory (`HostRebuildIndex_ReadsTheAppSettingsFileInTheWorkingDirectory`; before, it failed with "was not found and is not optional", because the file was checked in the working directory but looked for next to the program). The sample writes one there naming its own index file and audit file. Without a settings file it uses `./data/host.db`, `./data/audit.jsonl` and `./data/prompts` (`HostRebuildIndex_IndexesTheAuditFileInTheWorkingDirectory`).
- **The generated project is not built.** `ampelum new` writes a project that references the NuGet packages `Ampelum` and `SignalGrid.Ampelum.Testing`, version 0.9.0-alpha.6. They are not built from this repo and are not in the local NuGet cache. A restore of the generated project against an empty feed and an empty package folder (offline simulated) fails with `error NU1101: Unable to find package Ampelum. No packages exist with this id in source(s): ...` and `error NU1101: Unable to find package SignalGrid.Ampelum.Testing. No packages exist with this id in source(s): ...`. The test asserts the six files and their names only. `ampelum new` also needs the template installed first; the sample installs it into a private engine home.
- **Error mapping.** `ProblemDetailsMiddleware` is internal and the Host does not register it, so an unhandled exception inside an endpoint is not turned into one of the Host's error codes. The cases the endpoints handle themselves (unknown module 404, missing input 422, malformed body 400) are tested.
- **`ampelum repl`.** The CLI command builds a real chat client from the environment and refuses a fake. Only its refusal with a blank key is run; the REPL is shown through the library instead.
- **`ampelum eval`.** It scores predictions already in the dataset against the expected values. It calls no model, and `--signature` is only a label in the report.
- **Survey of discovered tools.** Without a manifest verifier, `McpToolSource` caps every tool a server lists to the most dangerous tier, whatever the server declares. The survey shows a tool declared safe that is governed as catastrophic, both for the in-process transport and for the served one.
- **The MCP server is minimal.** It answers `initialize`, `ping`, `tools/list` and `tools/call`, answers other methods with a JSON-RPC error and accepts notifications. It keeps no session and does no authentication or streaming, and it is not part of the library. The stdio server is the SDK's own server on its stdio transport.
- **`--fake` and MCP.** The HTTP and stdio parts run against servers of the sample, so `--fake` shows that the transport, the survey cap and the dispatcher work together; it does not show behavior against any other MCP server. The live path has never been run.
- **`DeclaredTierVerifier` trusts the server's own claim.** That is sound only because the stdio server is this program. Pointed at a server from elsewhere it would let that server declare any tool Safe.
